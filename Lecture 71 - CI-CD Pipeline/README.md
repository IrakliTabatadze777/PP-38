# მომხმარებელთა მხარდაჭერის აგენტი

ეს არის გამოგონილი ტურისტული აღჭურვილობის მაღაზიის მომხმარებელთა მხარდაჭერის აგენტი. ის აგებულია
FastAPI-ზე, LangChain-სა და LangGraph-ზე, ინტერფეისი კი Streamlit-ით არის დაწერილი. პროექტში
სამი იდეა ჩანს გვერდიგვერდ:

| იდეა | სად ჩანს |
| --- | --- |
| **RAG** — პასუხები პოლიტიკის დოკუმენტებიდან მოდის და წყარო დასახელებულია | `backend/app/rag/`, ინსტრუმენტი `search_knowledge_base` |
| **ReAct** — მოდელი თავად წყვეტს, რომელი ინსტრუმენტი გამოიძახოს შემდეგ | `backend/app/graph/` |
| **HITL**  — თანხის დაბრუნებამდე მიმომხილველი აუცილებლად ადასტურებს | `approval_gate`, `backend/app/api/approvals.py` |

ყველა მონაცემი გამოგონილია: რეალური გადახდები, მომხმარებლები და გადამზიდავები არ არსებობს.

## სტრუქტურა

```
backend/    FastAPI სერვერი, აგენტი (LangGraph), მონაცემთა ბაზის მოდელები, seed და ingest სკრიპტები
frontend/   Streamlit ინტერფეისი (ჩატი, მიმომხილველის რიგი, ცოდნის ბაზა)
docker/     PostgreSQL-ის საწყისი სკრიპტები (pgvector გაფართოება, სატესტო ბაზა)
docker-compose.yml
.env.example
```

## რა დაგჭირდებათ

- **Docker** (Docker Desktop ან Docker Engine + Compose)
- **Gemini API გასაღები** — შეგიძლიათ შექმნათ Google AI Studio-ში. გასაღების გარეშე სისტემა
  ეშვება, მაგრამ ასისტენტი გამორთულია (ცოდნის ბაზა არ ივსება და ჩატი არ პასუხობს).

ადგილობრივად გაშვებისთვის (Docker-ის გარეშე აპლიკაციისთვის) დამატებით გჭირდებათ Python 3.14.

## გაშვება Docker-ით (რეკომენდებულია)

1. შექმენით `.env` ფაილი:

   ```bash
   cp .env.example .env
   ```

2. `.env`-ში ჩაწერეთ:

   ```env
   GEMINI_API_KEY=თქვენი-გასაღები
   JWT_SECRET=ნებისმიერი-მინიმუმ-32-სიმბოლოიანი-საიდუმლო-ტექსტი
   ```

   `JWT_SECRET`-ის გენერაცია შეგიძლიათ ასე: `openssl rand -base64 32`.
   თუ `LLM_MODEL` ცარიელია, docker-compose იყენებს ნაგულისხმევ მოდელს (`gemini-3.6-flash`).

3. გაუშვით ყველაფერი:

   ```bash
   docker compose up --build
   ```

   ეს command უშვებს სამ სერვისს:

   | სერვისი | კონტეინერი | პორტი |
   | --- | --- | --- |
   | PostgreSQL 18 + pgvector | `support-db` | 5432 |
   | Backend (FastAPI) | `support-backend` | 8000 |
   | Frontend (Streamlit) | `support-frontend` | 8501 |

   backend-ის კონტეინერი ყოველ გაშვებისას ავტომატურად აკეთებს შემდეგს
   ([backend/docker/entrypoint.sh](backend/docker/entrypoint.sh)):
   - `alembic upgrade head` — ქმნის ცხრილებს;
   - `python scripts/seed.py --if-empty` — თუ ბაზა ცარიელია, ავსებს გამოგონილი მონაცემებით და სამი
     ანგარიშით; თუ მონაცემები უკვე არის, არაფერს შლის და მხოლოდ ნაკლულ ანგარიშებს ამატებს;
   - `python scripts/ingest.py` — პოლიტიკის დოკუმენტებს (`backend/data/kb/`) ბაზაში ტვირთავს
     (მხოლოდ თუ `GEMINI_API_KEY` მითითებულია).

4. გახსენით:

   - **http://localhost:8501** — ინტერფეისი (შესვლა ზემოთ მოცემული ანგარიშებით)
   - **http://localhost:8000/docs** — API დოკუმენტაცია (Swagger)
   - **http://localhost:8000/health** — სერვერის მდგომარეობა

გასაჩერებლად: `Ctrl+C`, ან ფონურ რეჟიმში გაშვებისას (`docker compose up -d --build`) —
`docker compose down`.

### თუ ბაზაში ძველი მონაცემები გაქვთ

`--if-empty` რეჟიმი არსებულ მონაცემებს არ ეხება. თუ ბაზა ადრე სხვა seed-ით იყო შევსებული
, `customer@example.com`-ს შეკვეთები არ ექნება. სუფთად
დასაწყებად აირჩიეთ ერთ-ერთი:

```bash
# ვარიანტი 1: მხოლოდ მონაცემების ხელახლა შევსება (ცოდნის ბაზა რჩება)
docker compose exec app python scripts/seed.py --reset

# ვარიანტი 2: ყველაფრის წაშლა, ბაზის მოცულობის ჩათვლით
docker compose down -v
docker compose up --build
```

## გაშვება ადგილობრივად (Docker მხოლოდ ბაზისთვის)

ეს მოსახერხებელია დეველოპმენტისას. ბრძანებები გაუშვით პროექტის ძირეული საქაღალდიდან.

1. **ბაზა:**

   ```bash
   cp .env.example .env     # შეავსეთ GEMINI_API_KEY და JWT_SECRET
   docker compose up -d db
   ```

   `.env.example`-ში `DATABASE_URL` და `CHECKPOINT_DB_URL` უკვე მიუთითებს `localhost:5432`-ზე
   Docker-ის ბაზაზე. `LLM_MODEL` ცარიელია, ამიტომ ლოკალურად ჩაწერეთ, მაგალითად:
   `LLM_MODEL=gemini-3.6-flash`. `.env`-ს backend კითხულობს პროექტის ძირეული საქაღალდიდან.

2. **Backend:**

   ```bash
   python3 -m venv .venv && source .venv/bin/activate
   cd backend
   pip install -r requirements.txt
   alembic upgrade head              # ცხრილების შექმნა
   python scripts/seed.py            # გამოგონილი მონაცემები + 3 ანგარიში
   python scripts/ingest.py          # ცოდნის ბაზის შევსება (სჭირდება GEMINI_API_KEY)
   uvicorn app.main:app --reload     # http://localhost:8000
   ```

3. **Frontend** (ახალ ტერმინალში):

   ```bash
   source .venv/bin/activate
   cd frontend
   pip install -r requirements.txt
   streamlit run app.py              # http://localhost:8501
   ```

   ინტერფეისი backend-ს ნაგულისხმევად `http://localhost:8000`-ზე ეძებს. სხვა მისამართისთვის
   დააყენეთ გარემოს ცვლადი `SUPPORT_API_URL`.

## seed სკრიპტი

[backend/scripts/seed.py](backend/scripts/seed.py) ავსებს ბაზას გამოგონილი მონაცემებით:

- 3 დემო ანგარიში (`customer@`, `reviewer@`, `admin@example.com`, პაროლი `support-demo`);
- 36 პროდუქტი (მათ შორის „საბოლოო გაყიდვის“ ნივთები), 50 მომხმარებელი და დაახლოებით 200
  შემთხვევითი შეკვეთა (შედეგი ყოველ გაშვებაზე ერთნაირია — seed ფიქსირებულია);
- `customer@example.com`-ის 7 სცენარული შეკვეთა (1042–1047, 1049), იხილეთ ქვემოთ;
- მიმომხილველის ისტორია: 3 უკვე გადაწყვეტილი მოთხოვნა (დამტკიცებული, შეცვლილით დამტკიცებული და
  უარყოფილი), მათთან დაკავშირებული თანხის დაბრუნებები და 2 ბილეთი (ერთი ღია, ერთი დახურული).

| ბრძანება | შედეგი |
| --- | --- |
| `python scripts/seed.py` | ავსებს ბაზას; თუ მონაცემები უკვე არის, შეწყვეტს მუშაობას შეტყობინებით |
| `python scripts/seed.py --reset` | წაშლის ყველა ცხრილის მონაცემს და თავიდან შეავსებს |
| `python scripts/seed.py --if-empty` | ბაზა ცარიელი არ არის — არაფერს შლის, მხოლოდ ნაკლულ ანგარიშებს ამატებს (ამას იყენებს Docker) |
| `python scripts/seed.py --users-only` | მხოლოდ ნაკლულ დემო ანგარიშებს ამატებს |

**მნიშვნელოვანი:** მიწოდების თარიღები გაშვების დღის მიმართ არის გამოთვლილი (მაგ. „3 დღის წინ“).
თუ რამდენიმე დღის შემდეგ დაბრუნდით და სცენარები აღარ ემთხვევა დაბრუნების ვადებს, გაუშვით
`python scripts/seed.py --reset`. `--reset` ცოდნის ბაზის (embedding-ების) ცხრილებს არ შლის.

> მოლოდინში მყოფი (`pending`) მოთხოვნები განზრახ არ ისახება: ის საჭიროებს შეჩერებულ აგენტს,
> რომელიც მხოლოდ რეალურ ჩატში ჩნდება. ახალი მოთხოვნა მიიღეთ ქვემოთ აღწერილი სცენარით.

## ყველაფრის შემოწმება: საცდელი სცენარი

1. გახსენით http://localhost:8501 და შედით `customer@example.com` / `support-demo`-თ.
2. ჩატში დაწერეთ: *„Order 1042 arrived with a broken zipper and I want my money back.“*
3. აგენტი შეკვეთაზე მითითებულ ელფოსტას გკითხავთ — უპასუხეთ `customer@example.com`.
4. ის მოძებნის შეკვეთას, წაიკითხავს დაზიანებული ნივთების პოლიტიკას, შეამოწმებს უფლებას და, თქვენი
   დადასტურების შემდეგ, მოითხოვს თანხის დაბრუნებას. გვერდი გაჩვენებთ, რომ მოთხოვნა გუნდთანაა.
5. გამოდით (Sign out) და შედით `reviewer@example.com`-ით. „Approval queue“ გვერდზე ნახავთ
   მოთხოვნას: თანხას, დაშვებულ მაქსიმუმს, ჩანაწერებს და პოლიტიკის წყაროებს. შეგიძლიათ
   **დაამტკიცოთ**, **შეამციროთ თანხა და დაამტკიცოთ**, ან **უარყოთ** მიზეზით.
6. ისევ შედით `customer@example.com`-ით — ჩატი განახლდება აგენტის პასუხით: თანხა უბრუნდება
   საწყის გადახდის მეთოდს 5–7 სამუშაო დღეში, პასუხი კი მიუთითებს დაბრუნების პოლიტიკას.
7. `admin@example.com`-ით შედით „Knowledge base“ გვერდზე და ნახეთ/მართეთ პოლიტიკის დოკუმენტები.

ტესტები იყენებენ ცალკე ბაზას `support_test` (მას `docker/initdb/01-init.sql` ქმნის ბაზის პირველ

## როგორ მუშაობს

აგენტი LangGraph-ის გრაფია: ერთი მოდელი, ექვსი ინსტრუმენტი და ოთხი node.

- **agent** — იძახებს მოდელს ინსტრუმენტებით და ითვლის გამოძახებებს.
- **approval_gate** — ყოველი *მგრძნობიარე* ინსტრუმენტისთვის (`issue_refund`,
  `issue_replacement`) ბაზაში ხელახლა ამოწმებს მოთხოვნას, ინახავს დასტურის ჩანაწერს და
  იძახებს `interrupt()`-ს. გრაფის მდგომარეობა PostgreSQL-ში ინახება და გაშვება ჩერდება.
- **run_tools** — ასრულებს გამოძახებებს: უსაფრთხოს პირდაპირ, მგრძნობიარეს — მხოლოდ თუ ამ
  კონკრეტული გამოძახებისთვის ადამიანის გადაწყვეტილება ჩაწერილია.
- **limit_escalation** — თუ ერთ შეტყობინებაზე მოდელი–ინსტრუმენტის 8 ციკლი ამოიწურა, ხსნის
  ბილეთს და მომხმარებელს აცნობებს, რომ ადამიანი დაუკავშირდება.

მიმომხილველის გადაწყვეტილება მოდის `POST /approvals/{id}/decision`-ით: სისტემა მას ინახავს და
შეჩერებულ გაშვებას აგრძელებს `Command(resume=...)`-ით. ნაკადის (thread) იდენტიფიკატორი ჩატის
იდენტიფიკატორია, ამიტომ საუბარი სერვერის გადატვირთვის შემდეგაც გრძელდება.

ავტორიზაცია JWT-ზეა აგებული: `POST /auth/login` აბრუნებს მოკლევადიან access ტოკენს და
refresh ტოკენს. როლები (`customer`, `reviewer`, `admin`) განსაზღვრავს, რომელ endpoint-ზე აქვს
მომხმარებელს წვდომა.
